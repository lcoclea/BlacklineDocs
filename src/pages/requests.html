Screens never change game data themselves. A button that buys, crafts or heals raises a request, a gameplay tag under NVS.View.Request, on the NVS View Request Subsystem. The built-in sources answer most requests on their own, and your game binds On Request to answer the rest or to mirror the change in its own systems.

How a request travels

  1. The player presses a button, drops an item or picks a menu row.
  2. The screen fills an FNVSViewRequest and calls Raise on its local player's request subsystem. The subsystem keeps the request in its history and broadcasts OnRequest.
  3. Every listener runs during the broadcast. Your game changes its own state here, or sends the change to its server.
  4. The screen offers the same request to every source it holds. A built-in source that knows the request changes its rows, such as the body zones healing on Heal all.
  5. The screen re-reads its sources and redraws, so a change made inside the broadcast shows at once.

The subsystem is a local player subsystem, so each local player has its own. Nothing is sent over the network.

Answer a request in Blueprint

The demo's player controller answers its requests this way. It handles Raid.Deploy by streaming in the chosen raid map, Raid.TimeOut by bringing the player home, and Task.ShowOnMap by opening the location screen.

  1. Get the subsystem In your player controller's Begin Play, add Get NVSViewRequestSubsystem, the local player subsystem getter, with Self as the player controller.
  2. Bind the event Drag from it and choose Bind Event to On Request. Create a custom event from the red pin. It receives one NVS View Request.
  3. Check the tag Break the request and compare Request Id with the tag you answer, using Equal (Gameplay Tag) and a Branch, or a Switch on Gameplay Tag for several.
  4. Use the payload Read Subject Id, Item Id or whichever fields the request uses. For Raid.Deploy, Subject Id names the raid map, and Get Raid Map Definition gives you its level.
You can add requests of your own. Make a gameplay tag, such as MyGame.Request.MarkJunk, and name it as the Action of an Item Action Definition. The item menu then offers the row and raises your tag when it is chosen. The demo adds a Mark as junk row exactly this way and answers Demo.Request.MarkJunk with a toast. Your own code can also call Raise on the subsystem, which is Blueprint callable.

Answer a request in C++

// MyUIBridge.h
#pragma once

#include "Subsystems/NVSViewRequestSubsystem.h"

#include "MyUIBridge.generated.h"

UCLASS()
class UMyUIBridge : public UObject
{
	GENERATED_BODY()

public:
	void Bind(ULocalPlayer* Player);

private:
	UFUNCTION()
	void HandleRequest(const FNVSViewRequest& Request);
};

// MyUIBridge.cpp
#include "MyUIBridge.h"

void UMyUIBridge::Bind(ULocalPlayer* Player)
{
	if (UNVSViewRequestSubsystem* Requests = Player->GetSubsystem<UNVSViewRequestSubsystem>())
	{
		Requests->OnRequest.AddDynamic(this, &UMyUIBridge::HandleRequest);
	}
}

void UMyUIBridge::HandleRequest(const FNVSViewRequest& Request)
{
	if (Request.RequestId == NVSViewRequests::RaidDeploy())
	{
		LoadRaid(Request.SubjectId); // Your own code. SubjectId names the raid map.
	}
	else if (Request.RequestId.MatchesTag(TAG_NVS_View_Request_Market))
	{
		SendToMarketServer(Request); // Every Market request is a child of this tag.
	}
}

The NVSViewRequests namespace has a function for every built-in tag, such as NVSViewRequests::ItemMove(). The native tags themselves are declared in Tags/NVSViewTags.h, so you can match a whole family with MatchesTag.

When your answer arrives later, for example from a server, call Refresh Source with the object that changed, or RefreshViewModels() on the open screen. See When a screen reads again.

The payload

Every request is one FNVSViewRequest. Each request uses a few fields and leaves the rest at their defaults.

FieldMeaning
FGameplayTag RequestIdWhat the screen asks for, such as NVS.View.Request.Item.Move.
FName SubjectIdThe record the request is about, such as a perk, a trader, a recipe or a raid map. None when there is no record.
FName ItemId, FText ItemName, FText ItemTagThe item the request moves or acts on.
FIntPoint ItemFootprint, bool bTurnedThe item's size in cells, already turned when bTurned says it lands a quarter turn from how it lies now.
FName TargetIdWhere the item goes. A doll slot for Item.Equip, a container for Item.Move.
FIntPoint TargetCellThe top-left cell on Item.Move and Item.Unequip. (-1,-1) takes the first free cell.
FName TargetBindingIdThe screen binding the item was dropped on, which tells two holders with same-named grids apart.
FName IntoIdThe container an unequipped item goes into. None means the stash.
FName WornItemIdFor an item taken off a doll, the worn item's own id. ItemId then names the slot.
int64 AmountA bid, a price or a quantity, by request.
FNVSViewListingDraft DraftThe sale type, buyout, opening bid and duration on Market.List.
FGameplayTagContainer ItemTags, FGameplayTag ItemFitsSlot, FGameplayTag ItemAttachKind, FGameplayTag ItemBlocksSlot, bool bItemUsableWhat the moved item is, copied from its row, so it stays wearable, usable and fittable wherever it lands.

With the plugin's own grids, a container id in TargetId is the grid's own id. With a container source of your own, the screen uses the binding id instead, such as Stash or Pack.

History and replay

The subsystem keeps every request in order, readable from C++ with GetHistory(). When a screen opens, it replays that history into the built-in sources it made fresh, so a screen opened later matches what the player did on earlier ones. A source you registered yourself is never replayed into, because it already holds the live state.

What you see

Open the health screen in the demo and press Heal all. The body zones fill, the cash drops by the price, and nothing in the demo's player controller had to answer it. Press Move out in the lobby and let the countdown finish, and the controller hears Raid.Deploy and streams the raid map in.
