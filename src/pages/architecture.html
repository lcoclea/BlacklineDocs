Read this page to decide whether Blackline fits your game. It covers the pieces the plugin is made of, where a screen gets what it shows, and how a screen asks your game to change something.

The short version

  • Layers stack screens by purpose: the HUD, menus over play, full menus, dialogs and toasts.
  • Screens are CommonUI widgets. Each screen class names the layer it opens on, and a screen registry maps a tag to each one.
  • Data assets hold your content, one asset per item, trader, task, station, raid map and so on. The plugin finds them by itself.
  • Sources hand live game state to the screens, such as health or the raid clock. The plugin has a built-in source for every screen, and you can swap any of them for a Blueprint of your own.
  • Requests are how a screen asks for a change, such as Buy or Heal all. The plugin answers many of them itself.
  • Empty states tell the player, and you, when a screen has nothing to show yet.

Layers

Every local player has one layer stack, held by UNVSViewLayerSubsystem. Which layers exist, their draw order and the input each takes come from a layout asset. The plugin ships DA_BlacklineLayout with five layers.

TagHolds
NVS.View.Layer.GameThe raid HUD
NVS.View.Layer.GameMenuScreens over live play, such as the raid inventory and the task log
NVS.View.Layer.MenuFull screen menus, such as the hub, stash, lobby and settings
NVS.View.Layer.ModalThe debrief, item windows, the match found banner and the drop countdown
NVS.View.Layer.NotificationToasts and the item context menu

The highest occupied layer that decides input sets the input mode. You never build the stack yourself: Show Screen By Tag, Show Screen and Open Loot Screen build it the first time they run. See Layers and screens.

Screens and the screen registry

Every screen derives from UNVSViewScreen, a CommonUI activatable widget. The plugin ships 21 screens and six windows and overlays, each a W_ Widget Blueprint under /NVSBlackline/Screens/ over a C++ class in NVSViewWidgets. They are listed on Screens.

The screen registry DA_BlacklineScreenRegistry maps each NVS.View.Screen.* tag to the Widget Blueprint that opens for it, with an optional layer override. Screens open each other through it. To restyle or extend a screen, make a Blueprint child of its W_ asset, then point the registry row at your child. Everything that opens that screen now opens yours.

Content is data

You create content in the Content Browser with right-click > Miscellaneous > Data Asset. The plugin registers every one of these types with the Asset Manager when it starts, under every content root, so a new asset shows up in the screens with nothing to configure.

Item DefinitionOne item: name, footprint in cells, weight, price, category, a type and any traits. See Items.
Item Category DefinitionA tab on the stash filter and the trade and market rails, such as Weapons or Medical.

Sources: live game state

Data assets describe things that do not change while the game runs. Values that do change, such as health, wind or the raid clock, come from sources. A source is any object that answers one of the plugin's interfaces. Each interface can be implemented in a Blueprint class or component.

InterfaceSupplies
NVS View Record SourceNamed records and lists of records
NVS View Meter SourceFigures with a range, such as health, wind or a wallet
NVS View Container SourceA grid's size and the items in it
NVS View Slot Set SourceA set of worn slots
NVS View Filter SourceThe options on a filter rail
NVS View Map Marker SourcePoints on a map
NVS View Market SourceThe player market
NVS View Setting Value SourceSetting values, read and written
NVS View Look SourceWhat items and characters look like, for the icon renderer
NVS View Item HolderA whole inventory, as the Inventory component holds one

Every screen binding names a built-in source class, such as UNVSViewVitals for the HUD's vitals. Most built-in sources read the data assets or the player's Inventory component. When a screen opens, it picks each binding's source in this order:

  1. An object given to that one screen with SetBindingSource.
  2. The binding's SourceObject, set in the Widget Blueprint.
  3. An object given to every screen with Set Screen Source, from NVS View Definition Library, naming the built-in source it replaces.
  4. A Screen Source Definition data asset that replaces that built-in source.
  5. The built-in source itself.

The usual Blueprint pattern is a component on the player that implements an interface, calls Set Screen Source on Begin Play, and calls Refresh Source whenever its values change. The demo's BPC_Vitals and BPC_RaidClock work this way. See Interfaces.

How data reaches a widget

  1. A screen is pushed onto its layer and activates. It walks its list of bindings.
  2. For each binding, the player's viewmodel registry hands back a viewmodel keyed by a domain tag and a context id. Two screens naming the same binding share one.
  3. The screen picks the binding's source in the order above.
  4. The viewmodel asks the source for its rows and writes its fields. Each changed field notifies the widgets that watch it.
  5. The screen fills its grids, rails and text from the viewmodels. When every binding the screen names for its empty state came up empty, it shows the empty state card.

Details are on Viewmodels.

Requests

A screen never writes your game's data directly. When the player presses Buy, Start craft or Heal all, the screen raises an FNVSViewRequest tagged NVS.View.Request.* on the local player's UNVSViewRequestSubsystem. Your game binds its On Request event in Blueprint and switches on the tag.

The built-in sources answer many requests themselves, including cash, crafting, healing and tasks, which is why the demo has no request code. After a request, the screen reads its sources again so the change shows. If your game answers later, call Refresh Source or Refresh View Models on the open screen. See Requests.

  1. The player presses Heal all on the health screen.
  2. The screen raises NVS.View.Request.Health.HealAll on the request subsystem, which broadcasts On Request.
  3. The screen offers the request to the sources it holds. The built-in health source treats every zone and the wallet pays for it.
  4. The screen reads its sources again and the bars refill.

Empty states

A screen can name the bindings that decide whether it has anything to show. When all of them come up empty, it lays a small card over its content with a title, a line for the player and, outside Shipping builds, a hint for you naming the data assets to create. Fourteen of the shipped screens have one. See Empty states.

Modules

The plugin descriptor is NVSBlackline. It holds five modules.

NVSView (Runtime)
Everything without a widget in it: the layer subsystem and layout asset, the viewmodels and their registry, the interfaces and built-in sources, the data asset types, the Inventory component, the raid session, deploy queue, request and notification subsystems, the style asset and the native gameplay tags.
NVSViewWidgets (Runtime)
Every screen class, the components (buttons, tiles, rows, toasts, grids), drag and drop, the item windows and UNVSViewScreenLibrary.
NVSViewRender (Runtime)
The icon renderer, which captures item looks into cached icons in an isolated studio world, and the character preview. See Rendering.
NVSViewSettings (Runtime)
The engine-backed settings, saved values, key binding profiles and the field of view modifier. See Settings.
NVSViewEditor (Editor)
The plugin icon and the class icons for Blackline data assets in the editor.

A Blueprint project needs none of this. A C++ game that calls the screen library links NVSView and NVSViewWidgets, and adds NVSViewSettings to read saved settings from code.

What it does not do

  • It does not replicate. The Inventory component and every subsystem are local to one player, so it is a single player kit as shipped. A networked game can supply its own inventory through the item holder and container interfaces.
  • It does not load levels. The deploy queue starts the raid session, and your game opens the raid map's level.
  • It ships no character art. The example characters come with the free Blackline Demo project. Without wardrobe pieces, the figure is a mannequin of basic shapes.
