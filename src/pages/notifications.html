Gameplay tells the player something by pushing a notification to the queue. The queue merges repeats, ranks by priority, holds less urgent toasts back while a menu is open, and the notification stack draws what is left. You describe each kind of toast as a data asset and push it with one Blueprint call.

Push a toast from Blueprint

The quickest way is a Notification Kind Definition asset, which holds everything about a kind of toast except its words.

  1. Make the kind Create a data asset from right-click > Miscellaneous > Data Asset and pick Notification Kind Definition. Give it a tag, such as MyGame.Notify.Extract, a priority, a duration and its colours. The plugin registers the type with the Asset Manager, so it is found without configuration.
  2. Get the queue In your player controller, add Get NVSNotifySubsystem, the local player subsystem getter, with Self as the player controller.
  3. Push it Call Push Kind on the subsystem with your kind asset, a title and a body. It returns false when the queue refused it.

Without a kind asset, call Push with a Make NVSNotifyPayload node instead and set the tag, priority and duration yourself. The demo does this when the player marks an item as junk. It pushes a payload tagged NVS.View.Notify.System at priority 1 for three seconds.

Notification Kind Definition

A toast takes the look of the kind whose tag matches its own most closely, so one kind can style a whole family of tags.

Tag
The notifications this kind styles. A child tag, such as MyGame.Notify.Extract.Late, takes this kind unless a closer kind exists.
Priority
From 0, the most urgent, to 4, the least. An urgent toast pushes a less urgent one out of a full stack.
Duration
Seconds on screen. Zero or less stays until dismissed.
Action Tag
When set, the toast shows an action button and a dismiss button. See Toasts the player acts on.
Accent, Title Role, Body Role, Surface, Border
Colour roles from the theme for each part of the toast. See Theming.
Draws Edge
Draws the accent as a bar down the toast's left edge.
Title Is Status
Puts the title at the right of the line as a status word instead of above the body.

A kind asset comes before the plugin's own look for a tag, so you can also restyle a built-in kind by making an asset with its tag.

The payload

A notification is an FNVSNotifyPayload. Push Kind fills the tag, priority, duration and action tag from the kind, and you give the words.

Tag
The identity, matched exactly. A second push with the same tag updates the first toast instead of adding one. A payload with no tag is refused.
Priority
Smaller is more urgent. Defaults to 4, the least urgent, so a payload that sets none never pushes out one that does.
Title, Body
The toast's two lines.
Duration
Seconds on screen. Defaults to 4. Zero or less stays until dismissed.
ActionTag
Makes the toast one the player can act on. Leave it empty for a toast that only informs.

Notifications are local to one player's machine. Push them where the replicated state arrives, such as a replication callback or a client event.

The queue

UNVSNotifySubsystem is a local player subsystem and ticks on the core ticker, so toasts count down while the game is paused. Everything pushed goes into one queue, one entry per tag, in arrival order. Three rules decide what shows.

Capacity

Up to four toasts show at once, and an open menu holds back up to four more. The Engine Settings Setup Definition's Max Visible Notifications and Max Held Notifications change both. The player's Notification density setting lowers what shows to one or three, or shows the full number on All. When the stack is full, an arrival pushes out the least urgent entry, the oldest among equals, but only if the arrival is strictly more urgent. Otherwise the push returns false and the arrival is dropped.

Repeats

A push whose tag is already queued replaces that entry's payload, priority included, adds one to its repeat count and restarts its timer. The toast keeps its place in the stack. Use one tag for a running ticker, such as salvage picked up, and it updates in place.

Holding back during menus

While the Menu layer has a screen, entries at priority 2 and below are held back. Priority 0 and 1 always show. Held entries do not count down. When the menu closes they rejoin the stack, least urgent dropped first if more come back than the stack holds, and the stack writes how many it is holding under the toasts.

  1. Your code pushes a task toast at priority 2 while the player has the stash open.
  2. No entry has that tag, so a new entry is made with its timer.
  3. The Menu layer is occupied and priority 2 can wait, so the entry joins the held group. Its timer does not run.
  4. The player closes the stash. The queue releases the held entries.
  5. The entry joins the stack and its timer starts. The stack redraws.
  6. When its duration runs out the entry is removed and the stack redraws again.

Removing toasts

Dismiss removes the entry under one tag at once, persistent or not, and returns false when nothing was queued under it. Dismiss All empties the queue. Both are Blueprint callable, as are the read functions Get Visible Entries, Get Suppressed Count, Is Menu Open, Num All Entries, Get Visible Capacity and Get Suppressed Capacity.

Toasts the player acts on

A toast whose payload has an action tag draws an action button and a dismiss button. Clicking the action raises the NVS.View.Request.Notify.Act request with the action tag, as a name, in its Subject Id, then dismisses the toast. Clicking dismiss only dismisses it. Your game answers the request on On Request, the same way it answers any other. See Requests.

Showing the stack

The queue works whether or not anything draws it. Two shipped screens read it:

  • W_NotificationStack sits on the Notification layer and draws the visible toasts with the held count under them. Open it once with Show Screen By Tag and NVS.View.Screen.NotificationStack after building the layers, and leave it there. It ignores Back, so Escape closes the menu under it.
  • W_RaidHUD draws the newest visible toast as a single HUD toast. While the HUD is the only thing showing, the stack hides its own toasts so they do not draw twice. When a game menu such as the raid inventory covers the HUD, the stack shows them again.

To build your own stack, bind UNVSViewNotifyQueueViewModel, which publishes Entries, EntryCount, SuppressedCount and bMenuOpen, and pass GetEntryObjects() to a List View with W_Toast as its entry. Each entry is a UNVSViewNotifyEntryViewModel carrying the payload, the repeat count and the time left. In C++, OnQueueChanged() fires at most once per change to what shows or what is held. A timer counting down does not fire it, but an entry expiring does.

Push from C++

#include "Engine/LocalPlayer.h"
#include "Subsystems/NVSNotifySubsystem.h"
#include "Tags/NVSViewTags.h"

void AMyPlayerController::NotifyTaskProgress(const FText& Step)
{
	ULocalPlayer* Player = GetLocalPlayer();
	UNVSNotifySubsystem* Queue = Player != nullptr ? Player->GetSubsystem<UNVSNotifySubsystem>() : nullptr;
	if (Queue == nullptr)
	{
		return;
	}

	FNVSNotifyPayload Payload;
	Payload.Tag = TAG_NVS_View_Notify_Task.GetTag();
	Payload.Priority = 2;
	Payload.Title = NSLOCTEXT("MyGame", "TaskTitle", "TASK");
	Payload.Body = Step;
	Queue->Push(Payload);
}

With a kind asset, call bool PushKind(const UNVSViewNotifyKindDefinition* Kind, FText Title, FText Body) instead. The priority constants live in the NVSNotify namespace: MostUrgentPriority (0), FirstSuppressiblePriority (2), LeastUrgentPriority (4) and DefaultDurationSeconds (4).

UNVSViewNotifyFeed is a data asset holding a list of payloads, and its PushAll pushes them all and returns how many the queue took. It is handy for testing how a stack of toasts looks.

What you see

With the stack open, push a task toast from gameplay. A toast with an accent edge appears bottom right and fades after its duration. Push the same tag again before it fades and the toast updates in place. Open the hub while a priority 2 toast is waiting, and it stays held, counted under the stack, until you close the menu.
