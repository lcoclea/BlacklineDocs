Viewmodels

A viewmodel holds what one part of a screen shows. The screen asks a source for data, the viewmodel keeps it and publishes each field, and the widgets redraw when a field changes. This page explains how viewmodels are keyed, which ones exist, how a screen ties them to widgets, and when a screen shows its empty state.

Where viewmodels sit#

  1. An object that answers one of the nine source interfaces, such as a built-in source or your own Blueprint component. See Connecting your game.
  2. A UNVSViewModel subclass that reads the source through its interface and publishes the result as FieldNotify properties.
  3. The screen resolves one viewmodel per binding when it opens and releases them when it closes.
  4. Grids, rails and text blocks named in the screen's binding tables draw the published fields.

Most games never touch a viewmodel directly. You change the source, and the viewmodel and widgets follow. Read on when you build your own screen or widget.

Domain and context keys#

Every viewmodel is resolved under an FNVSViewModelKey:

USTRUCT(BlueprintType)
struct FNVSViewModelKey
{
	/** What kind of viewmodel this is. */
	FGameplayTag Domain;

	/** Which one. An unset Guid is legal and names the single instance of its domain. */
	FGuid Context;
};

The context is what lets a stash, a backpack and a looted crate each have their own container viewmodel at the same time. Unreal's MVVM collection keys on class and name alone, so UNVSViewModelRegistry, a local player subsystem, folds both halves into one name and counts holders on each key.

UNVSViewModel* Resolve(const FNVSViewModelKey& Key, TSubclassOf<UNVSViewModel> ViewModelClass)
Returns the instance for the key, creating it the first time. Pair every call with one Release. Null for an invalid key, a null class, or a key already resolved as another class.
bool Release(const FNVSViewModelKey& Key)
Drops one holder. True only when this released the last holder and destroyed the viewmodel.

Screens call these for you. You only call the registry when you hold a viewmodel outside a screen.

Where a screen's context comes from#

The shipped screens build each binding with UNVSViewScreen::MakeBinding, which derives the context from the binding id. A reopened screen therefore gets the same key, and two screens that name the same binding id share one viewmodel. The raid HUD, the raid inventory and the loadout library all bind Vitals, for example.

When the player picks a record, such as a trader, the screen asks the binding again under that record's context, made from the record id. Your source receives these ids as its SetId, ContainerId or RecordId argument.

Three more are rows that a list viewmodel fills, so they have no source of their own: UNVSViewMapMarkerViewModel, UNVSViewNotifyEntryViewModel and UNVSViewSettingRowViewModel. A record list fills UNVSViewRecordViewModel rows the same way.

Each sourced viewmodel has the same entry points:

bool SetSource(const TScriptInterface<Interface>& InSource, const FGuid& Context)
Points the viewmodel at a source and a context, then reads it. The settings list takes a source only.
bool BindSourceObject(UObject* SourceObject, const FGuid& ContextId)
The same without naming the interface, which is what screens call. It checks ImplementsInterface, so Blueprint implementations work. False for an object that does not implement the interface. Blueprint callable.
bool Refresh()
Asks the current source again and publishes what changed. A selection held on the viewmodel survives.

SetSource and Refresh are Blueprint callable on every class except the market viewmodel.

Empty states#

A fresh install with no definition assets has nothing for most screens to list. Instead of drawing blank panels, fourteen screens show an empty state: a title, a sentence for the player, and a setup hint that names what to add.

The decision comes from the viewmodels. UNVSViewModel::HasContent() returns false while the source has given the viewmodel nothing to show, as the table above lists. A screen names the bindings that matter in its EmptyWhenBindings array, and when every one of them comes up empty it lays its empty state over its content. The text comes from three more class defaults:

EmptyTitle
The title, such as "No traders yet".
EmptyBody
One or two sentences the player reads under the title.
EmptySetupHint
What a developer needs to add for the screen to fill, such as which data assets to create. Shown in the editor and development builds, never in a shipped game.

Leave EmptyWhenBindings empty and a screen never shows one. The screens that do, and what each asks for, are listed on Screens.

How widgets get the data#

The shipped screens author no Blueprint graph. A screen fills its widgets from tables on its class defaults, each naming widgets in its tree:

ViewModelBindings
One FNVSViewScreenBinding per viewmodel: BindingId, Domain, Context, ViewModelClass, and the source, as SourceObject or the built-in SourceClass.
ContentBindings
Which viewmodel fills which grid, socket or container block. ElementId picks one element of a set, such as one meter.
RailBindings
Which repeated rail, a Dynamic Entry Box, gets one entry per published row.
ReadoutBindings
Which text block shows which published field, looked up by name, so a custom viewmodel's fields work too. MeterId reads a field of one meter in a meter set.

The screen subscribes to the FieldNotify field behind every readout, so text redraws on its own when a viewmodel publishes a new value. Grids and rails redraw when the screen pushes its content again, which RefreshViewModels and Refresh Source both do.

Reading a viewmodel from your own widget#

Call FindViewModel on the screen. It is Blueprint pure, and its output type follows the class you pass:

if (UNVSViewMeterSetViewModel* Vitals = Screen->FindViewModel<UNVSViewMeterSetViewModel>(UNVSViewRaidHUD::VitalsBindingId()))
{
	FNVSViewMeter Health;
	if (Vitals->FindMeter(TEXT("Vitals.Health"), Health))
	{
		HealthLabel->SetText(Health.ValueText);
	}
}

It returns null while the screen is closed, because the screen has released its viewmodels.

Keeping them current#

Viewmodels read their source when they bind and when asked. They do not poll, except the market screen, which asks once a second. When your values change, call Refresh Source with the object that changed. Every open screen that reads it refreshes the bindings that read it and redraws them.

Screens that share a binding id share the viewmodel, and each screen binds its own source to it when it opens. If you point one open screen at your object with SetBindingSource, a second screen naming the same binding rebinds the shared viewmodel to its own source when it opens. Register live sources with Set Screen Source instead. Every screen then resolves the same object and the shared viewmodel never switches.

What you see#

Open the demo's raid HUD with BPC_Vitals on the player controller. The health, food and water readouts are text blocks reading the Vitals binding's meter set, and they change on screen four times a second as the component redraws.
