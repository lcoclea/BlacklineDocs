How a screen is filled

Each screen has a list of bindings in its class defaults, ViewModelBindings. Every binding has an id, a viewmodel class and a built-in source class. The built-in sources read your data assets, the player's Inventory component and the plugin's own subsystems, so most screens fill as soon as the matching data assets exist.

Screens without a matching kind of data asset, such as the health zones, the lobby crew or the HUD compass, read sources whose rows you fill in yourself. You can do that with no code at all. Create a data asset whose class is the built-in source, such as NVSViewBodyZones, fill in its rows, then create a Screen Source Definition with Replaces set to that class and Asset set to your data asset. The demo does this for every such screen, with pairs such as Demo/Data/DA_PlayerBody and Demo/Sources/PDA_PlayerBodySource.

To feed a binding from live game state instead, make a Blueprint component that implements the binding's interface, pass it to Set Screen Source naming the built-in source it replaces, and call Refresh Source when its values change. The full order a screen picks its sources in is on Architecture, and the interfaces a source can answer are on Interfaces.

Buttons that change game data raise a request on the request subsystem. See Requests.

Empty states

A fresh install has no content, so a screen that lists content would open blank. Instead, fourteen screens show an empty state card in the middle of the screen. It has three lines:

  • A title, such as No traders yet.
  • One or two sentences for the player.
  • A setup hint for you, in the accent colour, naming what to create. It ends by saying the demo project shows the screen filled. The hint appears in the editor and in Development builds. A Shipping build never draws it.

The card shows when every binding the screen lists in EmptyWhenBindings comes up empty, such as a list with no rows or a set of worn slots with nothing in them. It goes away by itself as soon as one of them has content. The screen is still there underneath and clicks pass through the card, so anything the screen can still do keeps working.

Set or change an empty state

The empty state is four properties in the Empty State category of a screen's class defaults. Change them on your own child of the screen, so a plugin update does not undo your work.

  1. Make a child of the screen In the Content Browser, open /NVSBlackline/Screens/, right-click the screen's Widget Blueprint, such as W_TraderList, and choose Create Child Blueprint Class. Save it in your own folder.
  2. Point the registry at it Every screen opens through the screen registry. Make your own copy of DA_BlacklineScreenRegistry, set the row for the screen's tag to your child, then name your registry in Screen Registry on your View Setup Definition. Your setup wins over the plugin's. See Project settings.
  3. Edit the words Open your child, click Class Defaults and find the Empty State section in the Details panel. Change Empty Title, Empty Body and Empty Setup Hint. All three are text, so they localise like any other.
  4. Choose what counts as empty Empty When Bindings lists binding ids from the same screen's View Model Bindings, such as Roster. The card shows only when all of them are empty. Clear the list to turn the empty state off.
  5. Check it Press Play and open the screen in a project without that content. The card shows over the screen. It is not drawn in the Widget Blueprint designer.

You can give an empty state to a screen that has none, such as your own screen class, the same way. Two things to know:

  • The card is built inside the screen's CompositionBox size box. A Widget Blueprint without one cannot show an empty state.
  • A binding id in Empty When Bindings that the screen does not hold is logged as a warning on LogNVSView, and the screen never shows its card. See Troubleshooting.

From C++, UNVSViewScreen::IsShowingEmptyState() tells you whether the card is up. It is not exposed to Blueprint.

03 Raid HUD

The in-raid HUD: compass, weapon readout, vitals, limbs, the tracked task, exits, the raid clock, the crew and the newest toast. The weapon readout reads the gun worn in the primary slot, with its name, fire mode, the rounds in the fitted magazine (such as 30/30) and the spare magazines of that kind. Escape passes over the HUD to the screen below.

Asset/NVSBlackline/Screens/W_RaidHUD
ClassUNVSViewRaidHUD
LayerNVS.View.Layer.Game
Screen tagNVS.View.Screen.RaidHUD
Empty stateNone

What fills it

Three groups stay hidden until your game shows them with Reveal Hud Group: Nav (compass, tracked task and exits), Vitals (body, limbs, conditions and weapon) and Crew. The HUD reads no keys itself, so your controller decides when to reveal them. While the player stands in an exit, call Set Extract Progress each frame to fill the extract bar, and pass a value below 0 to hide it. The raid clock reads the raid session, which times the raid from the raid map's Raid Seconds. The demo feeds vitals from its BPC_Vitals component.

04D Health

Body zones with their hit points and conditions. The player picks a zone and treats it with a med from the stash. The zone's card lists which meds treat it, marked IN THE STASH or NONE IN THE STASH. A zone at 0 needs a med that heals. Heal all fixes everything for cash.

Asset/NVSBlackline/Screens/W_HealthScreen
ClassUNVSViewHealthScreen
LayerNVS.View.Layer.Menu
Screen tagNVS.View.Screen.HealthScreen

What fills it

The zones are the Zones list of the built-in UNVSViewBodyZones source. Fill it with a data asset made from that class and a Screen Source Definition that replaces it, as the demo's DA_PlayerBody and PDA_PlayerBodySource do. Meds are Item Definitions with the Consumable type, and Heals sets the hit points one gives back. Heal all costs HealPricePerPoint (10) for each missing hit point plus TreatmentPrice (150) for each untreated zone, both set on the same data asset.
